Tours written in code ship with deploys. When product managers or a CMS own the copy — or you want
to change a tour without a release — keep it as data. `fromJSON` turns a document into options for
`createTour`.

<Preview code={JsonDemoSource} title="JsonDemo.tsx">
  <JsonDemo client:visible />
</Preview>

```ts
import { createTour } from '@awesome-tour/react';
import { fromJSON } from '@awesome-tour/core/json';

const doc = await fetch('/api/tours/onboarding').then((r) => r.json());

export const onboarding = createTour(
  fromJSON(doc, {
    actions: { isAdmin: (ctx) => ctx.data.role === 'admin' }, // referenced by name in the JSON
    plugins: [persist(localStorageAdapter())],                  // anything createTour accepts
  }),
);
```

## The document

```json
{
  "$schema": "https://yorigcs.github.io/awesome-tour/schema/tour.schema.json",
  "id": "first-session",
  "version": 2,
  "rules": { "trigger": { "route": "/studio" }, "frequency": { "maxShows": 2 } },
  "steps": [
    { "id": "welcome", "title": "Your first session" },
    { "id": "mixer", "target": { "anchor": "mixer" }, "side": "left", "title": "Mixer" },
    { "id": "stems", "target": "#format-stems", "when": "isPro", "title": "Stems export" },
    { "id": "play", "target": "#play", "advanceOn": { "event": "click" }, "title": "Now play it" }
  ]
}
```

Everything a step can do is available, with two translations:

- **Targets** are selectors or [resilient locators](../targets/#resilient-targets) as objects —
  `{ "anchor": "mixer" }`, `{ "tour": "mixer" }` (`byTour`), `{ "role": "button", "name": "Export" }`
  (`byRole`), `{ "text": "Bounce" }` (`byText`), `{ "firstOf": [ … ] }` — or arrays of them. Content
  editors can point at what they see instead of writing CSS.
- **Functions** — `when`, `canNext`, `beforeEnter`, `beforeLeave`, `afterLeave`, `advanceOn.when`,
  a computed `next` (`{ "action": "pick" }`), `rules.audience` and `goal.when` — are action names
  resolved from `actions`.

## Validation

`fromJSON` validates first and throws one error listing every problem — unknown action names,
duplicate ids, `next`/`advanceOn.to` pointing at missing steps, values outside an enum (`side`,
`onTargetMissing`, `onTargetLost`, `layer`, `rules.frequency.once`) and malformed locators. Validate without throwing (e.g. in
a CMS preview) with `validateTourJSON(doc, actions)`, which returns the list.

The JSON Schema ships with the package — point your editor or CMS at it for autocomplete:
`@awesome-tour/core/schema.json`.

<Aside type="caution">
  A tour document controls what your users see. Load it from a source you trust, the same way you
  would load any remote configuration.
</Aside>

## Previewing drafts

Tours that live in a CMS need a way to try a draft on the real app before publishing it. Open any
page with `?tour-preview=<id>` and the provider loads the draft and runs it:

```tsx
import { fromJSON } from '@awesome-tour/core/json';

<TourProvider
  tours={publishedTours}
  preview={{
    // Fetch the draft (and check the user may preview it): return tour options, or null.
    load: async (id) => {
      const res = await fetch(`/api/tours/${id}/draft`, { credentials: 'include' });
      return res.ok ? fromJSON(await res.json(), { actions }) : null;
    },
  }}
>
  …
</TourProvider>;
```

A preview replaces the published tour with the same id while it runs, starts at `?step=` if
given, and is marked `tour.preview`: it saves no progress, records no impressions, sends no
analytics and ignores display rules — so previewing on production touches nobody's data. The
registry card shows a dashed "Preview" pill (`data-preview` on `Tour.Content`). Without React, use
`previewFromUrl(manager, { load })`.
